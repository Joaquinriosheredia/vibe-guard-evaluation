## Explicit conditions

1. **Sample sizes.**
   - **Python: n = 100** CRITICAL reviewed.
   - **Java: ≥ 50** CRITICAL reviewed, with a cap of **300** included Java repositories.
   - **If a language does not reach its sample, criterion 1 is NOT MET for that language,
     not "pending".**
   - The languages are evaluated separately. **Neither compensates for the other.**
2. **Precision.**
   - The **point estimate ≥ 90 %** (primary precision) decides.
   - The **Wilson 95 % interval and n are always published** next to it.
   - **Reaching 90 % as a point estimate does NOT show with 95 % confidence that the true
     precision is ≥ 90 %.**
3. **Noise.** **FP/1000 = (FP + U) / reviewed × CRITICAL / files × 1000**, threshold **≤ 5 per
   language**, justified below.
   - The original D2 volume (CRITICAL ≤ 5 and WARNING ≤ 20 per 1,000 files) is **published
     always**.
   - **U counts as FP.**
4. **Official verdicts: Joaquín only.**
   - The cards are generated by script: the whole function, every caller found by a literal
     search of the name in the repository, and a path class.
   - They are frozen, with their hash published, **before** the review.
   - The repository is always available to consult, at the pinned commit.
5. **Claude:** sealed blind verdicts. Their hash is published before Claude sees any of
   Joaquín's verdicts. **They never count.**
   - **Repeatability:** Joaquín reviews 10 cases again, at least 7 days after his first verdict.
6. **No criterion is modified after observing any result of test-corpus-2.** If a criterion
   is not met, that is documented, never adjusted.

## Question

These are the Definition of done criteria 1, 2 and 9, as amended for test-corpus-2:
- **1.** For each language, is the precision of vibe-guard's CRITICAL findings ≥ 90 %? It is
  measured on repositories never used to tune any rule, with the minimum n of that language.
- **2.** For each language, how many false CRITICAL alarms per 1,000 source files does a user
  get (FP/1000, which decides)? How many CRITICAL and WARNING findings in total (volume,
  published)?
- **9.** The precision is published with n, the review method and the confidence interval.

## Populations and search (fixed before any search)

Two independent pools: **Java** (directed by code signals) and **Python**. `scripts/select.mjs`
runs **once**, after this pre-registration is merged and `FROZEN.json` is filled. It uses the
GitHub REST repository search (`GET /search/repositories`), `sort=stars`, `order=desc`,
100 per page, up to the API cap of 1,000 results per query.
- Raw responses, UTC times and `total_count` per query go to `search-raw/`.
- `<D>` is the selection date (UTC) minus 183 days, as `YYYY-MM-DD`.
- **Every query of every pool runs at selection time**, including the Python expansion. No
  search runs later.

### Java pool (directed sample, not representative of all Java)

One query per topic `<T>`, exactly:

    topic:<T> language:Java fork:false archived:false is:public stars:>=50 size:100..1000000 pushed:>=<D>
    <T> ∈ spring-boot, spring-kafka, kafka, apache-kafka, spring-webflux, webflux,
          project-reactor, reactor, reactive, spring-cloud, microservices   (in this order)

**Code-signal gate (3g):**
- It is checked on the checkout at the pinned commit, **before the scan**, over the `.java`
  files outside the frozen wrapper's exclusions (the "file" definition below).
- Literal matches anywhere in the file text, comments included:

| Family | Present when |
|---|---|
| ASYNC | `@EnableAsync` in some file **and** `@Async` in some file (word boundary: `@AsyncResult` does not count) |
| KAFKA | `import org.springframework.kafka.core.KafkaTemplate;`, or `@KafkaListener`, or `import org.apache.kafka.clients.producer.KafkaProducer;` / `…Producer;` |
| REACTOR | `import reactor.core.publisher.Mono;`, `…Flux;` or `…*;` |

- A repository passes with **at least one family**. Its families are recorded, and results
  are also published per family.
- The signals describe the stack: they anchor the default CRITICAL rules of java-vibe-guard
  2.4.0 (`blocking`/`blocking-kafka`, `kafka-send-timeout`, `transactions`, `reactor-block`).
- **No signal is taken from vibe-guard's results or from the syntax its rules match.**
- The regular expressions are in `scripts/count-files.mjs` (`JAVA_SIGNAL_RES`) and tested in

## Run (`scripts/run.mjs java|python`)

For each candidate:
1. Shallow fetch of the pinned commit. HEAD must equal the pinned SHA.
2. Exclusions e and g.
3. Exactly this, with the defaults a user gets (default exclusions on, `--fail-on critical`,
   no `--exclude`):

       node <vibe-guard-scan>/bin/vibe-guard.js scan <checkout> --format json --output results/<pool>/<owner>__<repo>.json

- Exit 0 or 1 is a valid scan.
- Exit 2 is exclusion f.
- Per-repository timeout: 30 minutes. The whole process group is killed and the repository is
  treated as f.
- **A pool's measurement uses only the findings of its own language:** Java findings of the
  Java pool, and Python findings of the Python pool. The other language's findings are kept in
  the results and are not counted.
- Checkouts are kept only for repositories with at least one CRITICAL of the pool's language
  (they are needed for the cards). The others are deleted after the scan.

## Stopping rule (per pool, decided by counts only, never by verdicts)

**No finding is reviewed before both pools are frozen.**

| Pool | First batch | Next batches | Frozen when | Cap |
|---|---|---|---|---|
| Java | 25 included | 25 included | ≥ **50** Java CRITICAL in the pool | **300** included repositories |
| Python | 20 included | 10 included | ≥ **100** Python CRITICAL in the pool | **150** included repositories |

- The count is checked after each batch.
- A pool that reaches its cap, or runs out of candidates, is frozen with the count reached.
  **Criterion 1 is then NOT MET for that language.** The report says so with the count, and
  the threshold is never lowered.
- The pools stop independently.
- **Java phase 2:** it continues down the same frozen `candidates.json`, with the same queries,
  gate and rules, for up to 300 more included repositories. It runs only with Joaquín's
  explicit OK, as a later measurement under criterion 9 ("the sample is extended with the same
  pre-registered criterion"). It is reported separately and **never changes the test-corpus-2
  verdict**.

## Verdicts (the rules of test-corpus-1, unchanged)

Verdicts are decided from the source at the pinned commit. Callers and configuration are
followed anywhere in the repository.

- **TP** when all three hold:
  1. **Detection:** the code has the pattern the rule names, where it names it;
  2. **Context:** the conditions the message states for the impact hold there (the rule
     criteria below);
  3. **Reachability:** the code runs in the application's normal operation, as production
     code, not only in tests, examples, scripts or dead code.
- **FP** when any of 1–3 is false and the repository shows it.
- **Undetermined (U)** when the repository does not let 1–3 be decided: for example, the
  caller, the thread or the configuration lives outside the repository.

**Message accuracy** (criterion 8) is recorded separately, as overstated yes or no. A TP whose
message overstates the impact stays a TP for precision, and is counted apart.

**Rule criteria** (condition 2):

| Rule | TP context | FP context (examples, not exhaustive) |
|---|---|---|
| `blocking`, `blocking-kafka` | the blocking call runs on the anchored pool (an `@Async` executor with `@EnableAsync`, a scheduler, an event, a Kafka listener thread) on a normal path | the anchor is inert, or the call does not block (a completed future) |
| `kafka-send-timeout` | an untimed `.send(..).get()` on a normal path | the producer is configured so the call cannot wait beyond the message's bound |
| `transactions` (critical) | `@Transactional` and Spring's `@Async` on the same proxied method | not a Spring proxy, or not Spring's annotations |
| `reactor-block` (critical) | the call can run on a non-blocking Reactor thread (event loop, `parallel`, `single`) | it runs on a thread that may block (virtual, `@Async`, `boundedElastic`, startup, servlet worker) |
| PYVIBE-001/002/004/007/008/009/010/011/016/018 (blocking in `async def`) | the call runs on the event loop on a request or task path | the code runs only at startup or shutdown, in a thread (`to_thread`, executor), or in a `def` only called off the loop |
| PYVIBE-003/015 (nested loop) | reachable while a loop is running | only reachable with no running loop |
| PYVIBE-005 (Celery without a time limit) | the task can hang on external I/O and no global limit is set in the repository | a global `task_time_limit`/`task_soft_time_limit` covers it |
| PYVIBE-006 (ContextVar without reset) | the value can leak to later work sharing the context | the context is discarded after the call |
| PYVIBE-012/014 (discarded task) | no reference to the task is kept anywhere | a reference is kept (a set, a registry, a callback attaching it) |
| PYVIBE-013 (gather) | some gathered awaitable can raise on a normal failure, and the others then run unobserved | every awaitable contains its exceptions |
| PYVIBE-017 (empty `except`) | it can swallow `KeyboardInterrupt`/`SystemExit`, or errors that matter on a normal path | — |

A rule not listed falls back to conditions 1–3.

## Reviewers, cards and blindness

**Order of the steps:**
1. Both pools are frozen and the review set is drawn.
2. Claude generates the cards and commits their hash.
3. Claude writes its sealed verdicts and commits their hash.
4. Joaquín reviews.
5. Joaquín's verdicts are committed.
6. Claude's file is committed and must match its published hash.
7. The repeatability sample is reviewed, at least 7 days later.
8. `evaluate.py` runs.

**Official verdicts: Joaquín only** (`audit-joaquin.json`).
- Format: `{"reviewer", "verdicts": [{"id", "verdict": TP|FP|U, "reason", "overstated"}]}`.
- Each reason cites file:line evidence.
- `evaluate.py` refuses to run if any review-set finding lacks Joaquín's verdict. **There is no
  fallback to any other reviewer.**

**Cards** (`scripts/cards.py <WORK>` → `cards/<id>.md`): one per review-set finding,
generated by script from the checkout at the pinned commit. Facts only, never a verdict or an
assessment:
- the finding: rule, message, file:line, a link to the file at the pinned commit, and a
  **link to the whole repository at the pinned commit** (Joaquín may consult it freely at any
  time);
- **the whole enclosing function**, with line numbers and the finding's line marked:
  - Python: `ast`, decorators included;
  - Java: innermost method or constructor, by brace matching that skips comments, strings and
    character literals;
  - without an enclosing function, ±15 lines;
- **every match of a literal search of that function's name in the repository**:
  `git grep -n -w -F` over every tracked file, nothing filtered, all listed with path and line;
- **a path class** for the finding and for every match:
  - `test`: a segment `test`/`tests`/`testing`/`__tests__`, `src/test/`, or a test file name;
  - `example-or-script`: a segment `examples`, `example`, `scripts`, `script`, `wip`, `spike`,
    `demo(s)`, `sample(s)`, `docs` or `benchmark(s)`, but not inside `src/main/java` or
    `src/main/kotlin` (packages such as `com/example`);
  - otherwise `main`.

  The class is descriptive only: it does not decide anything.

**Freezing the cards:**
- The cards are generated once (`cards/` must not exist).
- `cards/SHA256SUMS` lists their sha256, and **the sha256 of `cards/SHA256SUMS` is committed
  before the review starts**.
- The cards are not edited afterwards.
- If Joaquín asks for more navigation on a finding, the request and the factual answer are
  logged with their date in `REVIEW-LOG.md`. The card stays as it was.

**Known limit of the literal search:** it does not resolve dynamic dispatch, reflection,
dependency injection or framework entry points. The whole function, with its annotations and
decorators, and the repository remain available for that.

**Claude's sealed verdicts** (`audit-claude.json`, the same format):
- Claude writes them from the frozen cards and the repository, **before seeing any verdict of
  Joaquín's**.
- The file stays outside the repository and only its sha256 is committed (`audit-claude.sha256`)
  before Joaquín starts. It is committed after Joaquín's verdicts and must match the hash.
- **They never count.** Published: raw agreement and Cohen's kappa over TP/FP/U against
  Joaquín's verdicts, plus the IDs that differ.

**Repeatability:**
- `scripts/sample.py repeat` draws **10** findings from the review set with
  `random.Random(20261023)`.
- Joaquín reviews them again, **at least 7 days after his first verdict on each**. He sees
  the card and not his first verdict.
- Published: raw agreement, kappa and the IDs that changed (`repeat-joaquin.json`). **His
  first verdict stays the official one.**

## Metrics and acceptance criteria (`scripts/evaluate.py`), per language

**Precision:**
- primary = TP / (TP + FP + U), with U counted against;
- secondary = TP / (TP + FP);
- Wilson score interval at 95 % for both.

**Criterion 1 (precision): MET for a language if, and only if:**
- at least the required n was reviewed (Python 100, Java 50); **and**
- the **primary point estimate is ≥ 90.0 %**.

Otherwise it is **NOT MET**, with the reasons. n and the Wilson interval are always published
next to it and never replace the point estimate in the verdict. **Reaching 90 % as a point
estimate does NOT show with 95 % confidence that the true precision is ≥ 90 %.** For
reference, if the true precision were exactly 90 %:
- with n = 50, an observed 90 % gives Wilson 0.786–0.957;
- with n = 100, it gives 0.826–0.945;
- the criterion would be met in only about 50–65 % of samples, whatever n (computed for n = 50 to 200).

**Criterion 2 (noise): MET for a language if the point estimate of FP/1000 ≤ 5.0.**

    FP/1000 = (FP + U) / reviewed × CRITICAL / files × 1000

- `CRITICAL` and `files` are full counts over the frozen pool, with no sampling.
- U counts as FP.
- Also published, without deciding:
  - the Wilson interval of (FP + U)/reviewed, scaled by the CRITICAL density;
  - a percentile interval from a bootstrap over repositories (2,000 resamples,
    `random.Random(20261024)`);
  - FP/1000 without U.
- **Justification of ≤ 5:**
  - ≤ 5 false CRITICAL alarms per 1,000 files is about **one false CRITICAL alarm every 200
    files**.
  - **It is a product tolerance threshold, not a scientific constant:** the burden of false
    alarms a team can absorb before it stops reading CRITICAL findings.
  - It keeps the number already committed in D2, and it was not calibrated on any measured
    density.
  - With a density like test-corpus-1's (35.49 CRITICAL per 1,000 Python files, development
    data), it corresponds to a precision of about 0.86. So criterion 1 is the binding one
    there, and criterion 2 binds when the density is high.

**Volume (original D2), published always, does not decide:**
- CRITICAL and WARNING (and MAJOR, INFO) per 1,000 files of each language;
- whether they are within CRITICAL ≤ 5 and WARNING ≤ 20.

**"Finding" and "file":**
- **Finding:** one entry of `findings[]` in vibe-guard's JSON, after its default exclusions,
  the engines' suppressions and deduplication, as a user sees it. Severity as reported.
- **File:** a `.java` (Java) or `.py` (Python) file of the checkout, counted by
  `scripts/count-files.mjs`. It uses the frozen wrapper's own `detect.js` and excludes the
  engines' default directories and the folders vibe-guard excluded (`excludes.applied`).
  `run.mjs` records whether those folders match the scan's.

**Informational, published, never deciding:**
- precision per rule, per repository, per Java family and per Python subpool;
- precision with each repository capped at 10 findings (`random.Random(20261022)`,
  repositories in sorted order);
- messages overstated;
- agreement with Claude's sealed verdicts;
- repeatability.

`evaluate.py` writes `metrics.json` and renders `METRICS.md` from it.

## Known limits (stated in the results)

- Topics are self-assigned, so a project without the topic is not a candidate.
- "Most starred among the search results" depends on the 1,000-result cap and on the
  activity window.
- `stars:>=50` / `>=100` and the window bias the corpus towards maintained, popular projects.
- The toy filter is lexical.
- **The Java pool is directed by stack signals and is not representative of all Java.**
- The expected Java yield is unknown: test-corpus-1 had 1 CRITICAL in 20 undirected
  repositories. **Java may not reach 50 within the cap.**
- The literal caller search has the limits stated above.
- `exclusions.json` inherits test-corpus-1's known limit: `100-repos.json` keeps only
  aggregates.
- Python findings are concentrated: in test-corpus-1, 3 repositories held 64 % of the
  CRITICAL findings. The capped precision and the repository bootstrap are published for that
  reason.
